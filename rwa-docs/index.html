Plant token architecture

How growtoo links a journal plant to an optional Solana Devnet plant token: standards, growth rewards, marketplace hold/settle, and planned redemption.

Who this is for: builders and curious adopters who want the plumbing. Regular growers can stay in the journal — you do not need this page to log watering. Prefer the honest product limits? Start with Risks & scope.

growtoo · public docs DEVNET

1. Architecture

Each physical seed you choose to tokenise is represented by a plant token (a Metaplex NFT in the verified growtoo Seeds collection). The NFT is the on-chain record; the public grow journal is the off-chain evidence trail. They link both ways: metadata references the journal plant ID, and the app shows mint address and transactions for each token.

Components

  • App (growto.live/app) — Firebase-authenticated grow journal. Optional Solana wallet (extension or watch-only) linked by a signed message.
  • Plant tokens — one per minted seed; strain, batch, and linked plant ID live in metadata (often Arweave via Irys).
  • $GROWTOO — fungible SPL reward token (9 decimals). Minted as plants advance stages; used as marketplace currency on Devnet.
  • Mint queue — mint/settlement requests in Firestore; an authority worker executes them on Devnet. Stand-in for future on-chain programs.

Trust model (Devnet MVP)

On Devnet, one collection authority also controls metadata updates, $GROWTOO minting, and marketplace hold/release. Stage updates only run after matching journal progress exists. Mainnet aims to replace the queue with an on-chain escrow program and stronger attestations — see Risks.

2. Token standards

Plant token (non-fungible)

Metaplex Token Metadata, extended with a machine-readable rwa block. Schema reference (legacy path may still use the older filename): seed-rwa.schema.json. 

{
  "name": "CBD Auto #1",
  "symbol": "SEED",
  "attributes": [
    { "trait_type": "Strain", "value": "CBD Auto" },
    { "trait_type": "Batch", "value": "B-2026-07-A" },
    { "trait_type": "Stage", "value": "Flowering" },
    { "trait_type": "Plant ID", "value": "plant-abc" }
  ],
  "rwa": {
    "standard": "growtoo/seed-rwa",
    "version": "1.0.0",
    "assetType": "flower",
    "strain": "CBD Auto",
    "batch": "B-2026-07-A",
    "plantId": "plant-abc",
    "cluster": "devnet"
  }
}

Metadata URI updates each growth stage; rwa.assetType flips from seed to flower at flowering so marketplace listings can distinguish them.

3. Growth minting flow

  1. Document growth in the journal and advance the plant token a stage in the app.
  2. The app files a growth-mint request for that mint address.
  3. The worker uploads stage metadata and updates the NFT metadata URI on-chain.
  4. The worker mints that stage’s $GROWTOO reward to the holder’s wallet.
  5. The app shows real transaction signatures (e.g. Solscan) in token history.

4. Marketplace (Devnet MVP)

  1. List: seller moves the NFT into a marketplace hold; listing goes live with a $GROWTOO ask.
  2. Invest: buyer pays $GROWTOO (instant sale or adopt-stake split).
  3. Settle: payment is confirmed; the plant token is released to the buyer. Sellers can cancel live listings.

Instant sale pays the full ask on buy. Adopt stake locks half until monthly care qualifies at harvest (all-or-nothing). Devnet settlement is operator-assisted; mainnet targets a fully on-chain program.

5. Redemption (planned)

Redemption would convert the on-chain asset into its real-world counterpart (harvest share), subject to regulation. Still mock / planned — not live fulfillment.

  1. Harvest-stage holder requests redemption in the app (planned).
  2. NFT is burned or marked redeemed.
  3. Operator records physical fulfilment against the batch and journal.
  4. $GROWTOO already earned stays with the holder; only the asset NFT is retired.

6. Deployed addresses (Devnet)

After deploy, addresses live in the repository (chain/deployed.devnet.json and the app chain config. Devnet only — no monetary value.
